
Actúa como arquitecto de software, desarrollador senior de Windows, especialista en audio digital, machine learning aplicado a separación musical, diseño de producto, seguridad y empaquetado.
Quiero que diseñes, programes, pruebes y empaquetes desde cero una aplicación de escritorio para Windows llamada Milo Split Pro.
Trabaja de forma autónoma hasta obtener una aplicación funcional y verificable. No te limites a describir código: inspecciona el entorno, investiga, implementa, compila, ejecuta pruebas reales y genera los artefactos finales.
Si encuentras una imposibilidad técnica o legal, no la ocultes ni simules que una función existe. Continúa con todo lo que sí pueda completarse y explica exactamente qué modelo, licencia, certificado, dispositivo o recurso falta.

1. Objetivo general
Milo Split Pro será una aplicación nativa de Windows para separar una mezcla musical en pistas independientes mediante modelos locales de inteligencia artificial.
Debe estar dirigida a músicos, productores, alumnos y usuarios sin conocimientos técnicos. El flujo principal será: cargar una canción, elegir qué separar, escoger una carpeta, procesar, escuchar las pistas y exportar.
Prioridades, en este orden:
1. Calidad real de separación.
2. Sincronización exacta de reproducción y exportación.
3. Estabilidad y ausencia de archivos silenciosos falsos.
4. Facilidad de uso.
5. Privacidad y procesamiento local.
6. Compatibilidad con Windows 10 y Windows 11.
7. Portabilidad del instalador.
8. Licencias y atribuciones correctas.
9. Diseño minimalista, bonito y trabajado.
No construyas una página web, una PWA ni una aplicación Electron.
Desarrolla una aplicación nativa de Windows. Prefiere C# con una versión LTS vigente de .NET, WPF y patrón MVVM por su madurez, estabilidad y acceso directo al sistema de audio. Puedes utilizar WinUI 3 solamente si verificas que el empaquetado, la reproducción multipista y la compatibilidad con las versiones objetivo son igual de fiables.
Antes de fijar versiones, comprueba la versión LTS actual de .NET y las versiones compatibles de Windows App SDK, WPF, NAudio y las demás dependencias. Registra todas las versiones de forma reproducible.

2. Entorno de construcción
La compilación final y las pruebas de Windows deben ejecutarse en Windows real o en un runner oficial de Windows.
Si Codex está trabajando desde macOS o Linux:
• Puede preparar arquitectura, código y documentación.
• Debe crear una automatización o CI para compilar en Windows.
• No debe afirmar que el EXE o instalador funciona si no se ha probado en Windows.
• Debe entregar una lista exacta de las pruebas pendientes en un equipo Windows.
Configura un proyecto reproducible mediante solución y proyectos .NET, archivos de bloqueo de paquetes, scripts PowerShell y una estructura de carpetas clara.

4. Flujo principal
El usuario debe poder:
1. Arrastrar una canción o seleccionarla con un diálogo nativo.
2. Ver nombre, formato, duración, frecuencia de muestreo y canales.
3. Elegir exactamente qué instrumentos desea separar.
4. Elegir una carpeta de trabajo y exportación mediante FolderPicker.
5. Iniciar la separación.
6. Ver progreso real y etapa actual.
7. Cancelar de forma segura.
8. Escuchar simultáneamente todas las pistas generadas.
9. Aplicar mute, solo y volumen independiente.
10. Cambiar el punto de reproducción mediante una línea temporal.
11. Exportar pistas individuales.
12. Exportar una mezcla con los volúmenes, mute y solo actuales.
13. Abrir la carpeta de resultados en el Explorador de archivos.
Nunca guardes resultados en una ubicación desconocida. El usuario debe elegir explícitamente la carpeta antes de separar.
Admite rutas con espacios, caracteres Unicode, nombres largos y unidades distintas a C:. No construyas comandos concatenando cadenas sin escapar.

5. Selector de pistas
La interfaz debe disponer de controles “Todas” y “Ninguna”, además de selectores individuales.
Categorías deseadas:
• Voces.
• Voz principal.
• Coros y segundas voces.
• Efectos vocales, reverberación o ambiente vocal.
• Ruido o artefactos.
• Batería completa.
• Bombo.
• Caja.
• Toms.
• Platos.
• Bajo.
• Guitarra.
• Guitarra acústica, solo si existe un modelo realmente capaz.
• Guitarra eléctrica, solo si existe un modelo realmente capaz.
• Piano y teclados.
• Otros instrumentos que puedan separarse mediante modelos reales y verificables.
• Other.
No muestres opciones falsas ni generes archivos silenciosos para aparentar que una separación existe.

6. Lógica de Other
La lógica de complemento es obligatoria.
• Si el usuario selecciona solamente “Voces”, exporta “Voces.wav” y “Other.wav”.
• Other debe contener todo lo que no sea voz.
• Si selecciona solamente “Batería”, exporta “Batería completa.wav”, sus detalles cuando corresponda, y “Other.wav”.
• Other debe contener todo lo que no sea batería.
• Si selecciona varios instrumentos, Other debe contener todo aquello que no haya sido seleccionado.
• Si selecciona todas las categorías, genera Other solamente si queda material residual real.
• Other no debe ser un archivo silencioso creado artificialmente.
• La suma de las pistas principales y Other debe reconstruir la mezcla con el menor error posible.
• Evita duplicar material cuando se exporta simultáneamente una pista general y sus subpistas.
Para voces detalladas:
• Voz principal y coros deben proceder de una separación real.
• Los efectos vocales no deben ser una copia de la voz.
• El ruido debe ser una pista independiente real.
• Ejecuta internamente las etapas necesarias aunque el usuario no haya seleccionado sus resultados intermedios.
• No obligues al usuario a entender dependencias entre modelos.

7. Investigación y motor de separación
Investiga modelos actuales antes de escogerlos. Utiliza fuentes primarias: repositorios oficiales, model cards, publicaciones de los autores y licencias incluidas con los pesos.
Condiciones obligatorias:
• Procesamiento completamente local.
• Sin subir canciones.
• Sin llamadas a APIs de pago durante la separación.
• Sin descargar modelos silenciosamente mientras se procesa una pista.
• Gestión explícita de la instalación de modelos.
• Hash SHA-256 de cada modelo.
• Registro de procedencia, versión, licencia, autor y capacidades.
• Diferenciación entre licencia del código y licencia de los pesos.
• Prohibición de asumir que los pesos son comerciales porque el repositorio sea MIT.
En una compilación distribuible utiliza únicamente modelos cuyos pesos tengan autorización inequívoca para uso, inclusión en aplicaciones, redistribución y uso comercial cuando corresponda.
Implementa un manifiesto con:
• Identificador.
• Ruta relativa.
• Hash SHA-256.
• Tamaño esperado.
• Versión.
• Origen.
• Licencia.
• Evidencia de licencia.
• Autor y atribución.
• Capacidades.
• Autorización de redistribución.
• Autorización comercial.
Implementa un verificador fail-closed. La compilación pública debe fallar ante un modelo no registrado, alterado, sin procedencia, sin autorización clara o sin las capacidades requeridas.
Puede existir una compilación experimental marcada como:
“COMPILACIÓN LOCAL DE DESARROLLO - NO DISTRIBUIR”.
No reduzcas la calidad únicamente para resolver una licencia. Si no existe un sustituto equivalente, informa del bloqueo y deja preparada la arquitectura para conectar un modelo autorizado posteriormente.

8. Arquitectura del motor Python
La interfaz nativa de Windows y el motor de machine learning deben estar separados.
Arquitectura recomendada:
• Aplicación C# como proceso principal.
• Motor Python local como proceso secundario controlado.
• Comunicación mediante JSON Lines, pipes con nombre o un protocolo local documentado.
• Salida estándar reservada para eventos estructurados.
• Salida de error y logs técnicos separados.
• Cancelación mediante señal controlada y limpieza de procesos hijos.
• Nunca utilizar cmd.exe con comandos construidos concatenando texto del usuario.
• Utilizar ProcessStartInfo.ArgumentList o un mecanismo equivalente seguro.
El cierre de la aplicación debe finalizar correctamente los procesos del motor sin dejar python.exe o procesos de inferencia ejecutándose.

9. Python propio y reproducible
No dependas del Python instalado por el usuario, Microsoft Store, Chocolatey, Conda, pyenv-win ni Visual Studio.
Incorpora un Python propio para Windows.
Requisitos:
• Versión exacta fijada.
• Fuente o distribución oficial verificable.
• URL y SHA-256.
• Arquitectura x64 como objetivo principal.
• Edición ARM64 separada solamente si todas las dependencias son ARM64 nativas.
• Ausencia de rutas del ordenador de compilación.
• PYTHONHOME y PYTHONNOUSERSITE configurados.
• Sin acceso a site-packages del usuario.
• Sin pip, setuptools o compiladores en el producto final, salvo necesidad demostrada.
• Cachés Python, Torch, ONNX y JIT fuera de Program Files.
• Registro de procedencia en PROVENANCE.json.
No copies una instalación arbitraria desde el ordenador del desarrollador. Construye o ensambla el runtime mediante un script reproducible y verifica todos sus binarios.

10. CPU, GPU y aceleración
La aplicación debe funcionar siempre en CPU, aunque sea más lenta.
Detecta de forma segura:
• CPU y memoria disponible.
• GPU NVIDIA compatible.
• CUDA/cuDNN solamente si la distribución elegida lo requiere y sus licencias permiten empaquetarlos.
• DirectML, ONNX Runtime u otra aceleración solamente cuando el modelo y la calidad estén verificados.
No presentes una opción de GPU que falle silenciosamente.
Requisitos:
• Selector Automático, CPU y GPU cuando corresponda.
• Fallback automático a CPU con explicación clara.
• Prueba previa de memoria antes de procesar canciones largas.
• División en segmentos sin perder continuidad.
• Mensajes comprensibles ante memoria insuficiente.
• Misma frecuencia de muestreo, duración y alineación independientemente del dispositivo.
• Comparación numérica entre CPU y GPU para detectar degradaciones importantes.
Evita incluir varios gigabytes de runtimes GPU si pueden suministrarse como paquete opcional. La edición CPU debe ser plenamente funcional.

14. Reproducción de audio en Windows
La reproducción debe comportarse como un mezclador multipista sencillo y preciso.
Utiliza un solo dispositivo de salida, un solo reloj y una sola línea temporal. Una opción adecuada es NAudio con WASAPI y un único MixingSampleProvider, siempre que la sincronización se demuestre mediante pruebas.
No abras un reproductor independiente y sin coordinación para cada pista.
Todas las pistas deben:
• Comenzar en el mismo sample.
• Conservar duración, canales y frecuencia de muestreo compatibles.
• Mantenerse sincronizadas durante toda la reproducción.
• Responder juntas a play, pausa, stop y seek.
• Compartir el mismo contador de posición.
Permite seleccionar el dispositivo de audio de Windows y reaccionar correctamente si se desconecta o cambia el dispositivo predeterminado.
Usa WASAPI compartido como modo estable por defecto. Añade modo exclusivo únicamente si está realmente probado y aporta valor.

15. Controles y comportamiento en tiempo real
Controles generales:
• Play.
• Pausa.
• Stop con semántica clara.
• Barra de progreso.
• Tiempo actual.
• Duración total.
• Clic y arrastre para hacer seek.
• Tecla espacio para alternar play y pausa.
El atajo de espacio no debe activarse al escribir en campos de texto ni mientras un diálogo modal esté abierto.
Comportamiento obligatorio:
• Mute no detiene la reproducción.
• Solo no detiene la reproducción.
• Volumen no detiene la reproducción.
• Estos cambios no devuelven el cursor al inicio.
• Seek continúa desde el punto seleccionado.
• Seek no produce rebote, doble ataque, clic o silencio perceptible.
• Utiliza crossfade o rampas de ganancia cortas.
• No reconstruyas innecesariamente todo el dispositivo de audio.
• Play después de pausa continúa desde la posición actual.
Gestiona cambios de dispositivo, suspensión del sistema y retorno desde suspensión sin dejar el motor bloqueado.

19. Rutas, permisos y datos mutables
Una aplicación instalada debe considerarse de solo lectura.

C:\Program Files\Milo Split Pro
Utiliza ubicaciones de Windows apropiadas:
• %LOCALAPPDATA%\Milo Split Pro para datos por usuario.
• %LOCALAPPDATA%\Milo Split Pro\Models para modelos descargables por usuario.
• %LOCALAPPDATA%\Milo Split Pro\Cache para cachés.
• %TEMP% para temporales de proceso.
• %PROGRAMDATA% solamente para datos compartidos que realmente lo necesiten.
• Carpeta elegida por el usuario para exportaciones.
No requieras privilegios de administrador para procesar audio.
Los temporales deben tener nombres únicos, limpiarse tras éxito y conservarse de manera controlada ante un fallo útil para diagnóstico.
Gestiona correctamente OneDrive, carpetas de red y unidades externas. No asumas que todos los archivos son locales o que permanecen disponibles durante todo el proceso.

29. Primera ejecución
Empieza en este orden:
1. Inspecciona el workspace y el sistema operativo actual.
2. Crea un inventario técnico.
3. Investiga modelos y prepara una tabla de licencias.
4. Elige WPF o WinUI 3 justificando la decisión.
5. Diseña la arquitectura C# y Python.
6. Presenta un plan de implementación.
7. Construye la primera versión funcional.
8. Ejecuta pruebas reales de audio.
9. Corrige los fallos.
10. Genera el instalador de Windows.
11. Ejecuta una instalación limpia.
12. Entrega artefactos e informe verificable.
Continúa trabajando hasta entregar el mejor resultado posible, sin simular capacidades inexistentes ni ocultar limitaciones legales, técnicas o de compatibilidad.
